System Architecture

ShopWave uses a microservices-inspired design where the FastAPI backend acts as the orchestrator for six internal MCP (Model Context Protocol) servers. Each MCP server owns a single bounded domain and is exposed via JSON-RPC 2.0 over HTTP/SSE. External clients (the React SPA) only ever talk to the FastAPI gateway — they never directly address an MCP server.

Communication Protocol — JSON-RPC 2.0

The FastAPI backend communicates with MCP servers using the standard JSON-RPC 2.0 protocol over HTTP POST. All calls include the internal API key in a custom header.

Request from FastAPI → MCP Server
{
  "jsonrpc": "2.0",
  "id": "req-uuid-here",
  "method": "tools/call",
  "params": {
    "name": "check_stock_levels",
    "arguments": {
      "product_ids": ["uuid-1", "uuid-2"]
    }
  }
}
Response from MCP Server → FastAPI
{
  "jsonrpc": "2.0",
  "id": "req-uuid-here",
  "result": {
    "content": [{
      "type": "text",
      "text": "{\"stock_levels\": [...], \"checked_count\": 2}"
    }]
  }
}

Installing Dependencies

ℹ️ Package Manager

The backend uses pyproject.toml (Hatchling build backend) — not requirements.txt. The frontend uses package.json with npm.

Backend (Python 3.14)

1
Create a virtual environment 
# From the project root:
python3.14 -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS/Linux:
source .venv/bin/activate
2
Install all production dependencies from pyproject.toml 
# The dot installs the current package (reads pyproject.toml)
pip install ./backend

# OR: navigate into backend first
cd backend
pip install .
3
Include dev dependencies (linting, testing) 
pip install "./backend[dev]"
# OR from within backend/:
pip install ".[dev]"
4
Install each MCP server's dependencies (each has its own pyproject.toml) 
pip install ./mcp-servers/inventory
pip install ./mcp-servers/payments
pip install ./mcp-servers/search
pip install ./mcp-servers/notifications
pip install ./mcp-servers/analytics
pip install ./mcp-servers/content

Frontend (Node.js ≥20)

1
cd frontend
npm install
2
Start dev server (requires backend running on :8000) 
npm run dev
# Opens at http://localhost:5173
# Proxies /api → http://localhost:8000 (see vite.config.js)
3
Production build 
npm run build      # outputs to frontend/dist/
npm run preview    # preview the built bundle locally

Running Locally (Without Docker)

⚠️ Prerequisite

You need PostgreSQL 18 running locally with the pgvector extension. Create database: CREATE DATABASE shopwave_db; and user shopwave.

1
Set DATABASE_URL to localhost in your .env 
DATABASE_URL=postgresql+asyncpg://shopwave:shopwave_pass@localhost:5432/shopwave_db
2
Apply migrations 
cd backend
alembic upgrade head
3
Start the FastAPI backend 
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
# API Docs: http://localhost:8000/docs
# OpenAPI JSON: http://localhost:8000/openapi.json
4
Start individual MCP servers (in separate terminals) 
# Terminal 2
DATABASE_URL=postgresql+asyncpg://shopwave:shopwave_pass@localhost:5432/shopwave_db PORT=8001 \
  python mcp-servers/inventory/server.py

# Terminal 3
RAZORPAY_KEY_ID=... RAZORPAY_KEY_SECRET=... PORT=8002 \
  python mcp-servers/payments/server.py

# (repeat for :8003, :8004, :8005, :8006)
5
Start the React frontend 
cd frontend && npm run dev

Backend Dockerfile — Multi-Stage Build

The backend Dockerfile uses two stages to minimize image size and attack surface:

Stage 1: builder (python:3.14-slim)

Installs gcc + libpq-dev needed to compile asyncpg. Builds a virtualenv at /opt/venv. This stage is discarded after build.

Stage 2: runtime (python:3.14-slim)

Copies only /opt/venv from builder. Runs as non-root user appuser:appgroup (UID/GID 1001). Exposes port 8000.

Frontend Dockerfile — Multi-Stage Build

Stage 1: builder (node:22-alpine)

Copies package.json + lockfile, runs npm ci, then npm run build. Outputs to /app/dist.

Stage 2: runtime (nginx:1.27-alpine)

Copies /app/dist to Nginx html root. Injects custom nginx.conf for SPA routing and API proxying.

Adding MCP Servers to docker-compose.yml

By default, MCP servers run as separate processes. To add them to Docker Compose:

# Add to docker-compose.yml services block:
mcp-inventory:
  build: ./mcp-servers/inventory
  container_name: shopwave_mcp_inventory
  restart: unless-stopped
  environment:
    DATABASE_URL: postgresql://shopwave:shopwave_pass@db:5432/shopwave_db
    PORT: 8001
  depends_on:
    db:
      condition: service_healthy
  networks:
    - shopwave_net
  # No ports: exposed — internal Docker network only (not host-accessible)

mcp-payments:
  build: ./mcp-servers/payments
  container_name: shopwave_mcp_payments
  restart: unless-stopped
  environment:
    RAZORPAY_KEY_ID: ${RAZORPAY_KEY_ID}
    RAZORPAY_KEY_SECRET: ${RAZORPAY_KEY_SECRET}
    PORT: 8002
  networks:
    - shopwave_net

# ... repeat pattern for mcp-search (:8003), mcp-notifications (:8004),
# mcp-analytics (:8005), mcp-content (:8006)

Database Migrations (Alembic)

Commands
# Apply all pending migrations (used automatically by Docker on start)
alembic upgrade head

# Generate a new migration from model changes
alembic revision --autogenerate -m "add product tags"

# Downgrade one step
alembic downgrade -1

# View current revision
alembic current

# View migration history
alembic history --verbose

# Run inside Docker container:
docker exec shopwave_backend alembic upgrade head
⚠️ pgvector Extension

Before running migrations, ensure the pgvector extension is installed on PostgreSQL: CREATE EXTENSION IF NOT EXISTS vector;. This should be in the first Alembic migration.

MCP Servers Overview

ShopWave uses the Model Context Protocol (MCP) to decompose business logic into isolated, independently deployable services. Each MCP server is a FastMCP application exposing tools via JSON-RPC 2.0 over SSE transport. The FastAPI backend is the sole consumer of these servers — they are never directly exposed to the internet.

⚠️ Internal Auth

All calls from FastAPI to MCP servers must include the X-MCP-API-Key header. Each MCP server validates this header against the MCP_INTERNAL_API_KEY environment variable. Requests without a valid key return HTTP 403.

MCPClient — How FastAPI Calls MCP Servers

The FastAPI backend uses an MCPClient helper class that wraps httpx.AsyncClient to send JSON-RPC 2.0 requests:

class MCPClient:
    def __init__(self, base_url: str, api_key: str):
        self.base_url = base_url
        self.headers = {"X-MCP-API-Key": api_key, "Content-Type": "application/json"}

    async def call_tool(self, tool_name: str, arguments: dict) -> dict:
        payload = {
            "jsonrpc": "2.0",
            "id": str(uuid4()),
            "method": "tools/call",
            "params": {"name": tool_name, "arguments": arguments},
        }
        async with httpx.AsyncClient(timeout=30.0) as client:
            resp = await client.post(
                f"{self.base_url}/mcp",
                json=payload, headers=self.headers,
            )
            resp.raise_for_status()
            result = resp.json().get("result", {})
            # MCP content is JSON-encoded in result.content[0].text
            content = result.get("content", [{}])[0].get("text", "{}")
            return json.loads(content)

Security — Authentication Flow

ShopWave uses a dual-token strategy combining short-lived access tokens with long-lived refresh tokens stored in HttpOnly cookies.

1. User submits email + password to POST /api/v1/auth/login │ ▼ 2. FastAPI hashes provided password with Argon2id → compares to stored hash │ (pwdlib[argon2] — memory-hard, resistant to GPU brute force) │ ▼ 3. On success → create_access_token(user_id, expires=15min) via PyJWT + create_refresh_token(user_id, expires=7days) │ ▼ 4. Response: Body: { access_token: "eyJ...", token_type: "bearer" } Cookie: Set-Cookie: refresh_token=eyJ...; HttpOnly; Secure; SameSite=lax; Max-Age=604800 │ ▼ 5. Client stores access_token in memory (Zustand authStore) — NOT localStorage │ ▼ 6. All protected requests: Authorization: Bearer {access_token} │ ▼ 7. On 401 → axios interceptor calls POST /auth/refresh (cookie sent automatically) → new access token issued → original request retried

JWT Structure

ClaimValue
subUser UUID (string)
iatIssued-at timestamp (UNIX epoch)
expExpiry timestamp (15 min for access, 7 days for refresh)
type"access" or "refresh"

Algorithm: HS256 using SECRET_KEY. For higher security environments, switch to RS256 with asymmetric keys.

MCPClient — Full Implementation

# backend/app/core/mcp_client.py
import json
from uuid import uuid4
import httpx
from app.core.config import settings


class MCPToolError(Exception):
    """Raised when an MCP server returns a JSON-RPC error response."""


class MCPClient:
    def __init__(self, base_url: str):
        self.base_url = base_url.rstrip("/")
        self._headers = {
            "X-MCP-API-Key": settings.MCP_INTERNAL_API_KEY,
            "Content-Type": "application/json",
        }

    async def call_tool(self, tool_name: str, arguments: dict) -> dict:
        """
        Execute a named MCP tool and return the parsed result.
        Raises MCPToolError on JSON-RPC errors.
        Raises httpx.HTTPStatusError on non-2xx HTTP responses.
        """
        payload = {
            "jsonrpc": "2.0",
            "id": str(uuid4()),
            "method": "tools/call",
            "params": {"name": tool_name, "arguments": arguments},
        }
        async with httpx.AsyncClient(timeout=30.0) as client:
            resp = await client.post(
                f"{self.base_url}/mcp",
                json=payload,
                headers=self._headers,
            )
            resp.raise_for_status()

        data = resp.json()
        if "error" in data:
            raise MCPToolError(data["error"].get("message", "MCP error"))

        content = data.get("result", {}).get("content", [{}])[0].get("text", "{}")
        return json.loads(content)

Production Checklist

🔐 Security

  • SECRET_KEY is a cryptographically random 32-byte hex (generated with openssl rand -hex 32)
  • MCP_INTERNAL_API_KEY is a 32-byte hex string generated with secrets.token_hex(32)
  • MCP servers are NOT exposed on public ports — internal Docker network only
  • Payment keys (RAZORPAY_KEY_SECRET) stored in Docker secrets or a secrets manager, not env vars
  • ANTHROPIC_API_KEY has usage limits set in the Anthropic console
  • DEBUG=false in production (disables FastAPI debug mode and traceback exposure)
  • TrustedHostMiddleware enabled with explicit allowed_hosts=[...]
  • HTTPS configured via reverse proxy (Nginx/Caddy) with valid TLS certificate
  • Refresh token cookie has Secure flag (requires HTTPS)

⚡ Reliability

  • Each MCP server has a HEALTHCHECK in its Dockerfile
  • FastAPI endpoints catch MCPToolError and return HTTP 502 with user-friendly message
  • MCP clients have timeout=30.0 set (prevents hanging requests)
  • Retry logic added to MCPClient.call_tool() for transient network errors
  • Database connection pool sized correctly: (2 × CPU_cores) + 1 workers
  • Alembic migrations tested in staging before production apply

📈 Performance

  • mcp-search uses a connection pool (not a new asyncpg connection per request)
  • Product embeddings are pre-generated at write time, not at search time
  • pgvector IVFFlat index created: CREATE INDEX ON products USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100)
  • mcp-analytics queries have indexes on orders.created_at and orders.status
  • Nginx gzip enabled for all text/JS/CSS assets
  • Vite static assets with content-hashed filenames cached with max-age=1y, immutable
  • Uvicorn workers set to (2 × CPU_cores) + 1

🔍 Observability

  • Structured logging (JSON format) added to each MCP server for log aggregation
  • OpenTelemetry traces span both FastAPI → MCPClient → MCP server calls
  • Alerts configured for MCP server health check failures
  • Database slow query logging enabled (log_min_duration_statement = 500)
